# Allira Bot

Telegram-бот с двумя ИИ-персонажами в крипто-тематике. **Аллира** — дерзкая
крипто-трейдерша, **Лэйн** — тихий технофилософ. Живут в личке и в группах,
ведут диалог с памятью, играют турниры на кубиках, постят новости в канал,
считают доход от аренды NFT на Marketapp **и ведут крипто-бухгалтерию по
нормам РФ** (НК РФ ред. 418-ФЗ: 3-НДФЛ с FIFO и прогрессивной шкалой).

Бот на русском языке, вся техническая документация в коде — на русском.

## Возможности

- **ИИ-чат в ЛС** — отвечает на любые сообщения, помнит последние 8 пар реплик.
  Персонажа выбирает сама по теме: крипта → Аллира, технологии → Лэйн.
- **Живой чат** — разметка ответа (`*курсив*`, `**жирный**`, код, ссылки),
  индикатор «печатает…», который продлевается, пока модель думает, реакция
  на сообщение и быстрые ответы кнопками под ответом. Ошибки сети и лимитов
  показываются голосом персонажа, а не служебным текстом.
- **Правда вместо выдумок** — в промпт крипто-персонажа подставляется блок
  живых данных рынка с правилом «только эти цифры»: топ, лидеры роста и
  падения, TON. `/market` — тот же срез по запросу.
- **Режиссура длины** — по природе запроса выбирается сценарий (на «привет»
  — две фразы, на «расскажи подробно» — развёрнуто), его цифра уходит в
  промпт, а после ответа убираются вступления («Конечно!») и хвосты-вопросы
  («хочешь подробнее?»). Если модель растянула ответ, следующий план
  жмётся сильнее.
- **Память диалога** — история хранится раздельно по персонажам, чтобы
  Аллира и Лэйн не путали друг друга. `/clear` очищает контекст.
- **Инлайн-режим** — `@AlliraCryptoQueen_bot <вопрос>` из любого чата.
- **Турнир на кубиках** — регистрация, 1-на-1 или все-против-все, таблица
  победителей. Состояние турнира живёт в БД и переживает рестарт сервиса.
- **Автопостинг** — живые данные по крипте (CoinGecko + RSS-новости) и NFT-рынку
  TON (Marketapp + TonAPI): цены, капитализация, тренды, заголовки новостей,
  флор коллекций, аренда и лоты в продаже. Тема поста крутится между криптой,
  NFT и их связкой, раз в 12-14 часов, со сгенерированной картинкой.
- **Отчёты Marketapp** — доход от аренды NFT: ежедневный, недельный, месячный.
  Синхронизация событий из блокчейна через TonAPI с чекпоинтом прогресса.
- **Статистика** — `/stats`, `/history`, `/leaderboard`.
- **Крипто-бухгалтерия** — учёт всех операций (аирдропы, покупки, продажи,
  майнинг, стейкинг, обмены, переводы) и формирование 3-НДФЛ отчёта
  по требованиям ФНС РФ.
- **Автосинк с Bybit и OKX** — раз в час бот сам забирает спотовые сделки,
  ончейн-депозиты и выводы по read-only ключам и записывает их двойной
  записью, без ручного экспорта CSV.
- **Сверка дебет-кредит** — `/reconcile` проверяет парность проводок,
  отрицательные остатки и сверяет расчёт с фактическими балансами
  TON-кошельков и бирж.

### Сервис управления

Два интерфейса с общей логикой (`utils/bot_admin.py`):

- **Telegram-меню `/admin`** — статус бота (аптайм, фоновые задачи, БД),
  кошельки с вкл/выкл, последние операции, настройки ФНС, ручные запуски
  (синк бирж, скан TON, сверка Дт/Кт) и последние строки лога — кнопками.
- **Веб-панель `/admin`** на том же порту, что и `/health`: те же данные
  плюс добавление/удаление операций и кошельков, фильтры по активу и типу,
  результат сверки с остатками. Включается переменной `ADMIN_PANEL_TOKEN`
  (без неё панель отдаёт 401); вход по токену, заголовок `X-Admin-Token`
  или `?token=`. Наружу отдаются только признаки «ключ задан/не задан» —
  сами секреты панель не показывает.

Последние 400 строк лога бот держит в памяти (`utils/log_buffer.py`) и
отдаёт обоим интерфейсам — на бесплатном хостинге нет места на диске,
а для диагностики хватает свежих строк.

**Типы операций** (`<type>` для `/addtx`):
- Доходы: `airdrop`, `mining`, `staking`, `reward`, `interest`, `gift_in`, `refund`, `income_other`
- Расходы (реализация): `sell`, `swap_out`, `spend`, `gift_out`, `sell_nft`, `disposal_other`
- Торги/конвертации (двойная запись, создаются автоматически CEX-синком):
  `buy` (покупка актива), `trade_in` / `trade_out` (приход/списание quote-валюты
  по сделке). Участствуют в балансе и FIFO, но не образуют самостоятельной
  налоговой базы — выручка отражена по парной стороне сделки.
- Внутренние перемещения: `transfer_in`, `transfer_out` (не влияют на налоговую базу)

**Поддерживаемые цепочки** (`<chain>` для `/wallet_add`):
`ton`, `evm`, `btc`, `tron`, `solana`, `other`

## Локальный запуск

```bash
git clone https://github.com/Hinorum/Allira.git
cd Allira
python -m venv .venv && source .venv/bin/activate   # Windows: .venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env   # Windows: copy .env.example .env
python main.py
```

Бот поднимется в режиме polling. Ручка живости: `http://localhost:10000/health`.

**Не запускай локальную копию с тем же `BOT_TOKEN`, что на Render.** Два
процесса с одним токеном делят обновления Telegram между собой, и в логах
появляется `Conflict: terminated by other getUpdates request`.

## Деплой на Render

Репозиторий содержит `render.yaml` с готовым blueprint — при создании сервиса
Render подхватит настройки сам.

```bash
curl https://render.com/docs/static.yaml \
  -o "$(git config --get remote.origin.url | sed \
  -E 's|git@(.+):(.+)/(.+).git|\1/\2/\3|')/render.yaml"
```

### Чтобы бот не засыпал

Бесплатный инстанс Render засыпает после ~15 минут без внешнего трафика. Polling
Телеграма делает только исходящие запросы и таймер не сбрасывает, поэтому
нужен внешний пинг.

1. [UptimeRobot](https://uptimerobot.com) → **Create a new monitor**
2. Тип **HTTP(s)**, интервал **5 minutes**
3. URL: `https://<твой-сервис>.onrender.com/health`

Заодно получишь уведомление, если бот упадёт.

## Крипто-бухгалтерия: что внутри

### Метод расчёта себестоимости

**FIFO** (по умолчанию): при реализации актива списание идёт с самых старых
лотов — те единицы, что пришли первыми, уходят первыми.

**WAC (средневзвешенная)**: реализация по средней цене всех открытых лотов
актива. Переключение через `/tax_setup МЕТОД=wac`.

### Налоговая база

- **Доход** = сумма продаж + стоимость аирдропов/майнинга/стейкинга на
  дату получения по рыночной котировке.
- **Расход** = документально подтверждённые затраты на приобретение
  (FIFO-себестоимость списанных единиц).
- **База** = доход − расход. Если расход превысил доход от реализации,
  межкатегорийный взаимозачёт с доходами от аирдропов НК РФ не допускает —
  бот сообщит об этом в замечаниях.
- **Себестоимость доходного актива** (аирдроп, майнинг, стейкинг) равна
  нулю: по НК расходов при получении нет. Рыночная оценка такого актива —
  это доход, а не расход, и себестоимостью лота она не становится. Для
  покупок наоборот: цена покупки — это и есть себестоимость лота.

### Двойная запись и сверка «дебет-кредит»

Каждая операция — это пара проводок. Покупка 1 BTC за USDT на бирже
записывается автоматически как **Дт BTC (BUY) / Кт USDT (TRADE_OUT)**,
продажа — **Дт USDT (TRADE_IN) / Кт BTC (SELL)**. Аирдроп — **Дт Актив /
Кт ДОХОДЫ (ст. 214 НК)**. Это закрывает две типичные ошибки ручного учёта:
«деньги от продажи не появились» и «актив ушёл в минус без прихода».

`/reconcile [год]` прогоняет три контроля:

1. **Парность.** У каждой продажи/покупки ищется парная проводка валюты.
   Непарные операции и операции без RUB-оценки (нет котировки) попадают
   в список расхождений с указанием `tx_id`.
2. **Отрицательные остатки.** Списания превышают приходы — признак
   незаписанной покупки или аирдропа.
3. **Баланс-контроль.** Расчётные остатки по журналу сверяются с
   ФАКТИЧЕСКИМИ: TON-кошельки через TonAPI, биржи Bybit и OKX через
   их read-only API. Допуск — 1% на комиссии.

Фоновая задача `reconcile_sync.py` повторяет сверку ежедневно в 03:30 и
шлёт уведомление в ЛС при появлении расхождений (повторное напоминание —
раз в 7 дней, пока проблема не уйдёт). Итог выгружается в XLSX командой
`/reconcile_xlsx`: листы «Сводка», «Проводки», «Расхождения», «Балансы».

### Прогрессивная шкала НДФЛ (ст. 224 НК РФ, резидент)

| Доход, ₽/год | Ставка |
|---|---|
| до 2 400 000 | 13% |
| 2 400 000 – 5 000 000 | 15% с суммы превышения |
| 5 000 000 – 20 000 000 | 18% с суммы превышения |
| 20 000 000 – 50 000 000 | 20% с суммы превышения |
| > 50 000 000 | 22% с суммы превышения |

**Нерезидент** — 30% со всего дохода (п. 3 ст. 224 НК РФ).

**Майнер** — доход от добычи полезных ископаемых облагается по **отдельной**
шкале 13/15/18/20/22% (пп.1.1 п.2 ст. 224 НК РФ): она не суммируется с
прочими доходами, и в разбивке отчёта видно, к какой базе относится ступень.
Доход от майнинга признаётся в момент получения по рыночной котировке.
Расходы на электричество и оборудование в MVP не автоматизированы — вводятся
вручную через `/addtx mining` с соответствующим комментарием; при
формировании отчёта они пока учитываются как нулевые (планируется:
автоматический учёт расходов на пул). Доход от продажи намайненного
имущества относится к общей базе — разделить его по лотам нельзя, о чём
отчёт предупреждает.

### Курсы

- Цена крипты — историческая из [CoinGecko](https://coingecko.com).
- Курс USD→RUB — ежедневный из [ЦБ РФ](https://www.cbr-xml-daily.ru).
- Всё кэшируется в SQLite (`fiat_rates`), повторно API не дёргается.

### Источники операций

- **Ручной ввод** — `/addtx` или `/airdrop`.
- **Импорт выписки биржи** — `/import` или `/autoimport` реплаем на файл:
  CSV **или Excel (.xlsx)**. Заголовки распознаются сами: Bybit, OKX,
  Binance и русские («Дата и время», «Торговая пара», «Тип операции»,
  «Количество», «Цена», «Сумма») — порядок колонок значения не имеет.
  Поддерживаются покупки, продажи, вводы и выводы; отменённые сделки
  (статус «Cancelled»/«Failed») отбрасываются. Цена в выписке биржи — это
  **quote-валюта** пары (USDT, BTC и т.п.), а не рубли, поэтому перевод в
  рубли делает `price_oracle` по курсу на дату сделки: для стейблкоинов —
  курс ЦБ. Если котировки нет, сделка записывается без рублёвой оценки и
  попадает в отчёт как «нет котировки», а не как заведомо неверное число.
  Импорт идёт тем же путём, что и API-синк, — с двойной записью
  (покупка → `Дт` актива / `Кт` quote-валюты, продажа → наоборот).
- **Автосинк CEX** — фоновая задача раз в час (`tasks/cex_sync.py`)
  забирает спотовые сделки Bybit и OKX по read-only ключам и раскладывает
  их двойной записью: покупка → `Дт` актива / `Кт` quote-валюты, продажа →
  наоборот. Bybit отдаёт историю только окнами по 7 дней, поэтому сделки
  читаются последовательными окнами с cursor внутри каждого; OKX —
  через `fills-history` (последние 3 месяца) с пагинацией по `billId`.
  Комиссии сделок (`execFee`/`feeCurrency` у Bybit, `fee`/`feeCcy` у OKX,
  колонка `fee` в выписке) уменьшают выручку продажи или увеличивают
  себестоимость покупки; в примечании остаётся исходное значение.
  Начало покрытия истории запоминается по каждой бирже: `/autoimport`
  и `/tax` предупреждают, если API не дотягивает до 1 января отчётного
  года (OKX — 3 месяца, Bybit — 2 года), и подсказывают импортировать
  выписку за недостающий период.
  Тем же прогоном подтягиваются **ончейн-депозиты и выводы**
  (Bybit `/v5/asset/deposit/query-record` и `/v5/asset/withdraw/query-record`,
  OKX `/api/v5/asset/deposit-history` и `/api/v5/asset/withdrawal-history`):
  успешный депозит пишется как `TRANSFER_IN`, вывод — как `TRANSFER_OUT`.
  Внутренние (off-chain) переводы внутри биржи не берутся — это не
  блокчейн-движение. У переводов отдельный водяной знак с перекрытием
  7 дней, чтобы позднее подтверждение вывода не потерялось. Дубли
  отсекаются по `external_id`, так что повторные прогоны безопасны.
  Статус — `/cex_status`, форсзапуск — `/cex_sync`; после синка сразу
  запускается сопоставление переводов.
- **Сканер кошельков** — фоновая задача раз в 15 минут (`utils/chain_scan.py`)
  читает историю переводов по зарегистрированным адресам: TON — через
  TonAPI `/accounts/{addr}/events` (нативный TON и Jetton'ы), EVM — через
  Etherscan V2 (`tokentx` + `txlist`, один ключ на все сети).
  Классификация — в `utils/auto_import.py`, см. следующий раздел.

### Автоимпорт: источники → один прогон → налоговая база

Смысл: человек отдаёт минимум — **адреса кошельков одним сообщением** и,
если есть биржа, **read-only ключи в ENV**. Дальше не нужно помнить порядок
команд: есть один экран `/autoimport` и одна кнопка «Обновить всё».

```bash
/wallet_add                 # без аргументов — бот ждёт список адресов
0:abc… основной             # каждый с новой строки, сеть определится сама
0x123… биржа                # можно с подписью
# или сразу: /wallet_add 0x123…
/autoimport                 # источники, готовность, «Обновить всё»
```

Как это работает:

1. **Скан.** По каждому адресу забирается история переводов.
2. **Сопоставление с биржей.** Входящий перевод на кошелёк ищет
   «вывод с биржи» из выписки или API-синка (тот же актив, та же сумма,
   ±3 дня); исходящий — «ввод на биржу». Совпавшая пара — это
   **перемещение**: актив учтён лотом в месте покупки, второй раз он не
   считается.
3. **Классификация** остальных переводов:
   - входящий с неизвестного адреса — **доход** (аирдроп, ст. 214 НК);
   - исходящий на неизвестный адрес — **реализация**;
   - в одной транзакции ушёл актив и пришёл другой — **обмен**: реализация
     уходящего и приобретение пришедшего (себестоимость = отданная сумма);
     раньше приход в обмене считался аирдропом, и один обмен облагался
     дважды;
   - перевод между своими кошельками — перемещение.
4. **Проверка.** Всё неоднозначное попадает в список на проверку
   (`/autoimport` → «Требуют проверки»): под каждой операцией три кнопки —
   «↔️ Перемещение», «⬆️ Доход», «⬇️ Реализация», по одному тапу. Если
   выписка или синк биржи появятся позже, уже записанный «ложный доход»
   пересопоставится и исчезнет сам. Если с классификацией всё верно — одна
   кнопка «✅ Подтвердить всё».

«Обновить всё» — тот же прогон, что и фоновая задача: скан кошельков, синк
Bybit/OKX (сделки, депозиты, выводы) и повторное сопоставление переводов
в одном заходе. Раньше после одного лишь `/cex_sync` вывод с биржи оставался
«доходом», пока человек не догадается ещё раз открыть `/autoimport`. Теперь
`/cex_sync` тоже сразу сопоставляет переводы; отдельный импорт выписки
остаётся для совместимости и старых периодов.

Ключевое правило учёта: **актив учитывается ровно один раз — там, где он
появился**. Перемещения (биржа ↔ кошелёк, кошелёк ↔ кошелёк, биржа ↔ биржа)
не создают ни дохода, ни расхода, ни нового FIFO-лота: они помечены
`is_internal` и не влияют ни на налоговую базу, ни на расчётный остаток.

### Расходы, уменьшающие базу

Кроме себестоимости проданного актива, из дохода вычитаются и прочие
документально подтверждённые расходы (ст. 221 НК РФ): электричество у
майнинг-пула, комиссии за вывод средств, амортизация оборудования.
Комиссии самих сделок бот уже учитывает автоматически — уменьшает
выручку продажи или увеличивает себестоимость покупки, поэтому вручную
их дублировать не нужно.

```bash
/tax_cost 50000 2025 электричество      # расход за год
/tax_cost СУММА=12000 КАТЕГОРИЯ=комиссии # или так
/tax_cost                                # список расходов
/tax_cost_del 3                          # удалить
```

До этого такие расходы некуда было записать: поле `manual_costs` в отчёте
было объявлено, но всегда оставалось нулём — база майнера считалась
завышенной на всю сумму добычи, а комиссии не попадали в расчёт вовсе.
Расходы видны и в сводке, и в PDF/XLSX (в XLSX — отдельный лист
«Расходы» с расшифровкой).

### Что бот НЕ делает

- **Не формирует XML для ЛК ФНС.** Только PDF/XLSX/CSV — для сверки
  и подготовки данных. Готовый машинный формат 3-НДФЛ — задача отдельного
  сервиса, не входит в этот MVP.
- **Не тянет внутренние (off-chain) переводы между биржами.** Автосинк
  забирает только ончейн-депозиты и выводы. Перевод внутри Bybit/OKX по
  UID/email и перевод между биржами без блокчейна остаются ручными —
  `/addtx transfer_in` / `/addtx transfer_out`.
- **Не сканирует NFT.** У NFT нет котировки, и в базу они бы попали мусором.
- **Не докручивает историю OKX глубже трёх месяцев** — спотовый
  `trade/fills-history` отдаёт ограниченное окно. Для старых сделок
  остаётся `/import` с выпиской. Бот не молчит об этом: `/autoimport`
  и `/tax` показывают, с какой даты покрыта история, и предупреждают,
  если начало налогового года старше окна API.

## Путь «от операции до отчёта»

Раньше путь был длинным и требовал памяти на синтаксис:

```
/wallet_add ton <адрес>        завести кошелёк
/addtx airdrop BTC 0.001 15.01.2025   × N — по команде на операцию
/tax_setup ИНН=… ИМЯ=… СТАТУС=…   настроить отчёт
/tax 2025                      посчитать
/tax_pdf 2025                  выгрузить
```

Теперь:

| Шаг | Как стало |
|---|---|
| вообще не вводить операции | `/autoimport`: пришли адреса списком, подключи read-only ключи бирж, нажми «Обновить всё» — бот сам соберёт историю переводов, сделки и посчитает базу |
| записать операцию | `/addtx` без аргументов — пошаговая форма (кнопки + одно число) |
| записать много операций | обычный текст: `15.01 получил 0.5 BTC, 20.06 продал 0.3 BTC за 2.4 млн` — бот разберёт и покажет предпросмотр перед записью |
| настроить отчёт | кнопка прямо в сводке: ИНН → ФИО → статус, три вопроса подряд |
| выбрать год | кнопки «📅 2026» / «📅 2025» в сводке, не надо набирать |
| проверить перед подачей | кнопка «⚖️ Сверить с сетью» прямо в сводке |
| поправить спорную операцию | кнопки «↔️ Перемещение / ⬆️ Доход / ⬇️ Реализация» под записью в `/autoimport` |

Разбор списка идёт через LLM, поэтому всегда показывается предпросмотр:
числа, типы и даты видно до записи, и каждая строка проходит ту же
проверку, что и ручной ввод. Битые строки в предпросмотре не показываются.

### Очередь запросов

Все обращения к LLM (чат, инлайн-режим, автопостинг) идут через общую
очередь `utils/llm_queue.py`:

- обслуживание строго **FIFO** — кто раньше спросил, тот раньше получил;
- одновременных запросов два: на бесплатном тарифе OpenRouter четыре
  параллельных вызова гарантированно ловили 429;
- ожидающий получает сообщение «⏳ В очереди N», которое исчезает вместе
  с ответом;
- при переполнении (32 запроса) бот честно говорит, что очередь занята, а
  не молчит.

Состояние очереди видно в панели (`/admin` → «В очереди LLM») и в
`/admin`-меню бота.

### Главное меню

`/start` открывает витрину из шести разделов: **Портфель**, **Операции**,
**Отчётность**, **Аренда подарков**, **Турнир**, **Спросить**. Внутри
раздела — конкретные команды с примерами и кнопки-быстрые действия:
нажал «💰 Портфель» — получил сводку по портфелю, ничего не набирая.

Раньше в `/start` было две кнопки при тридцати командах, а `/help` был
простынёй текста без навигации.

В групповом чате меню «/» короткое — `/start`, `/help`, `/market`, `/clear`,
`/history`, `/leaderboard`. Налоги, кошельки, операции и модерация в общем
чате не всплывают: это личные команды, и Telegram показывает их только в
личке с ботом (у админов — плюс `/ban`, `/unban`, `/kick`). Обработчики при
этом никуда не делись — набранная руками команда сработает и в группе.

## Автопостинг: откуда берутся данные

Каждый пост собирает факт-лист из живых API и кладёт его в промпт. Модель
получает явный запрет выдумывать цифры — в пост попадают только те числа,
которые пришли из API.

| Источник | Что даёт | Ключ |
|---|---|---|
| [CoinGecko](https://coingecko.com) `/coins/markets` | топ по капитализации, цены, 24ч/7д, объём | не нужен |
| CoinGecko `/search/trending` | тренды поиска | не нужен |
| CoinGecko `/global` | капитализация рынка, объём, доминация BTC/ETH | не нужен |
| RSS [CoinDesk](https://www.coindesk.com) и [Cointelegraph](https://cointelegraph.com) | свежие заголовки новостей (до 36 ч) | не нужен |
| Marketapp `/v1/collections/` | флор, аренда, объём 7/30 дней, держатели, тираж | `MARKETAPP_API_KEY` |
| Marketapp `/v1/rent/{gifts,usernames,numbers}/` | живые лоты аренды по всем категориям | `MARKETAPP_API_KEY` |
| Marketapp `/v1/gifts/onsale/` | лоты в продаже, минимальная цена | `MARKETAPP_API_KEY` |
| [TonAPI](https://tonapi.io) `/v2/nfts/collections/…` | описание, тираж и цены лотов коллекций из `NFT_COLLECTIONS` | не нужен |

Тема поста крутится: `crypto` → `nft` → `mixed`, причём последние две темы
не повторяются подряд. Если источник недоступен, его блок просто выпадает
из факт-листа, а пост уходит по оставшимся данным — без придуманных цифр.
Падение одного источника не уносит остальные: блоки собираются независимо.

В посте о NFT в факт-лист попадают только те новости, что про NFT и TON,
в посте о крипте — все свежие заголовки. Заголовок новости приходит из
чужого RSS, поэтому в промпте он помечен как данные, а не как инструкция.

Снапшот рынка в чате (`utils/market.py`) и данные для постов
(`utils/market_data.py`) читают один и тот же кэш CoinGecko — на канал и в
чат уходит один запрос, а не два.

## Данные

Всё хранится в SQLite-файле `allira.db` рядом с кодом.

На бесплатном Render файловая система **эфемерная**: при каждом деплое файл
пересоздаётся, история и портфель обнуляются. При этом простое контейнера
в спящий режим диск **сохраняется** — турниры в процессе игры переживают
засыпание.

Если данные нужно сохранять между деплоями — нужен платный диск или внешняя
база.
